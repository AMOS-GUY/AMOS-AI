## 6. Security findings

See SECURITY_AUDIT_M0_5 for evidence. Totals: **0 critical, 0 high, 1 medium (fixed), 4 low**
(2 fixed, 2 open), **8 informational**.

- **SEC-01 (Medium, fixed):** with Node's env-proxy mode on, local-model traffic was tunneled through
  `HTTP_PROXY`. Reproduced experimentally; the transport now refuses.
- **SEC-02 (Low, open):** the parent directory of the data dir is not checked.
- **SEC-03 (Low, fixed):** doctor leaked the environment to helper processes.
- **SEC-04 (Low, fixed):** credentials and query strings were accepted in provider URLs.
- **SEC-05 (Info, fixed):** config and transport had two loopback definitions.
- **SEC-06 (Low, open):** CI actions are pinned by tag, not SHA.
- **SEC-07 … SEC-13 (Info):** documented limits, including the gate's `build`-contract and `GET`
  URLs, no encryption at rest, and Windows having no permission checks.

## 7. Linux findings

- The laptop meets every M0 requirement (Node 24.22.3 ≥ minimum; also satisfies REA's ≥ 24.22.1).
- The reported M0.1 results match expectations exactly, including the 15 POSIX tests.
- **Unprivileged user namespaces work today** (`kernel.apparmor_restrict_unprivileged_userns = 0`).
  M2 must not assume this stays true across OS updates; doctor must re-check it at startup.
- AMOS uses Node's bundled SQLite. A system `sqlite3` version is irrelevant to it.
- Nothing in M0 binds a port. The server binding is schema-restricted to loopback (verified on the
  laptop: `0.0.0.0` rejected).
- **Dev PC vs laptop:** the dev PC runs Node 24.18.0 while the laptop and (inferred) CI run 24.22.3.
  Upgrading the dev PC removes that gap and its missing security fixes (an owner action).

## 12. Remaining risks

1. **M0.5 code is untested on Linux.** It is OS-independent, but the laptop re-run (P4) has not
   happened.
2. SEC-02 and SEC-06 are open (Low).
3. Provider behaviour with real keys is unknown (capabilities, streaming quirks, content filtering,
   rate limits).
4. Local model performance on the laptop is unmeasured and may be too slow for agentic use.
5. `node:sqlite` is release-candidate stability (ADR-003).
6. The dev PC runs an older Node than the laptop and CI.
7. The gate's `build`-contract and `GET`-URL limits (SEC-07) depend on code review in M1.

## 13. Recommendations

1. Push, then re-run `npm run check` and `doctor` on the laptop (closes P4).
2. Decide P1–P3 and P5 (M1_LAUNCH_GATE), then start M1a with the provider adapter against local
   Ollama.
3. Upgrade the dev PC's Node to 24.22.3.
4. Fix SEC-02 as part of M1a's first persistence commit.
5. Pin CI actions by SHA.
6. Write the sandbox and path-guard design notes before M2, and the remote-access ADR before M5.

## 14. Final readiness assessment

**CONDITIONAL GO for M1a** (M1_LAUNCH_GATE). The foundations are implemented, tested and
Linux-validated (as reported), and the one medium finding is fixed. M1a waits only on your
decisions and the laptop re-run. M1b and anything tool-related stay behind their own conditions.
This is not a statement that AMOS is "secure": it is a statement that the M0/M0.1 guarantees hold
as tested, with the limits listed above.
